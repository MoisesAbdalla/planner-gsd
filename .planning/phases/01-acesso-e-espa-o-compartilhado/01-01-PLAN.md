## Phase Goal

**Goal (ROADMAP.md, verbatim):** Duas pessoas conseguem entrar com a conta Google e compartilhar um mesmo espaço de dados, isolado de qualquer outro, com o app já em português e usável no celular

> **Nota de MVP mode:** a linha `**Goal:**` da Fase 1 no ROADMAP.md **não está no formato de user story** (`As a … / I want to … / so that …`). Ela foi transcrita acima literalmente e nenhuma história foi inventada. Para formalizar a história, rode `/gsd mvp-phase 1` — isso não bloqueia a execução desta fase.

<objective>
Provar, de ponta a ponta e em uma única fatia fina, que o stack inteiro desta fase funciona: um usuário entra com a conta Google, um espaço é criado para ele no Firestore com ele como membro, e o nome desse espaço volta para a tela lido do banco. Nada de convite, nada de categorias, nada de shell visual — só o caminho mais fino que atravessa build, Firebase, Security Rules, autenticação, camada de dados e UI.

Purpose: o projeto é greenfield (o diretório contém apenas `.planning/`). Errar a arquitetura aqui custa uma migração depois. Esta fatia é produção, não protótipo: as regras, os helpers e o provider criados aqui são os mesmos que as fases 2–6 herdam.

  <name>Checkpoint: modelo de membership do espaço compartilhado (porta de sentido único)</name>
  <decision>Como o espaço compartilhado guarda a lista de membros: array `memberIds` no documento do workspace, ou subcoleção `/workspaces/{id}/members/{uid}`</decision>
  <context>
    D-05 travou que **não há limite de membros** — o modelo precisa suportar N pessoas desde o início. O que D-05 não decidiu é a **representação**: a modelagem de dados foi delegada explicitamente em Claude's Discretion. Esta é a decisão mais irreversível da fase: a forma escolhida entra na função `isMember()` e, a partir dela, na Security Rule de **toda coleção das fases 2 a 6** (`transactions`, `recurringBills`, `billOccurrences`, `creditCards`, `cardInvoices`, `purchases`, `installments`, `categories`, `monthlyBudgets`, `tasks`, `taskOccurrences`, `reminders`).

    Desfazer depois não é refatoração: é migrar todo documento de workspace já gravado e reescrever cada bloco `match` do `firestore.rules`, com os dois usuários reais em produção no meio do caminho.

    A pesquisa (`01-RESEARCH.md` §Alternatives Considered) recomenda o array, e `research/ARCHITECTURE.md` já assume `memberIds` em todo o desenho das fases seguintes. A opção pela subcoleção não está errada — ela evita reescrever o array inteiro a cada entrada — mas diverge do padrão que o resto do projeto já pressupõe.
  </context>
  <options>
    <option id="member-ids-array">
      <name>Array `memberIds: string[]` no documento `/workspaces/{workspaceId}` (recomendado)</name>
      <pros>Uma única leitura resolve a checagem de membership (`request.auth.uid in resource.data.memberIds`); `isMember()` custa um `get()` por avaliação de regra; é o que `research/ARCHITECTURE.md` já assume nas fases 2–6; permite a regra de entrada por convite comparar `memberIds` antes e depois com `.concat([uid])`, que é o mecanismo central do desenho do convite.</pros>
